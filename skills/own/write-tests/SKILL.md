# Purpose

用于围绕已有功能或修复内容补充测试思路，帮助建立覆盖核心路径、边界情况和回归风险的测试方案。

# Instructions

1. 先理解现有实现与改动目标，再决定测试范围。
2. 优先覆盖核心业务路径、容易回归的分支和已知缺陷场景。
3. 明确区分单元测试、集成测试和端到端测试的适用范围。
4. 如果暂时无法直接编写测试代码，至少输出完整的测试设计与用例清单。
5. 当上下文不足时，明确指出缺少的依赖、测试框架或入口信息。

# Focus

- 核心业务是否被覆盖
- 边界条件和异常路径是否可验证
- 本次改动是否有明确回归测试点
- 测试粒度是否合理
- 测试是否有助于长期维护

# Output

请按以下结构输出：

1. 测试目标
2. 建议测试层级
3. 核心测试用例
4. 可补充的边界场景
5. 如可实现，再给出测试代码建议

# Constraints

- 不要脱离实际代码结构写空泛测试建议。
- 不要为了追求覆盖率而堆砌低价值测试。
- 不要忽略错误分支、空状态和异常输入。
- 如果无法直接落地测试代码，要明确阻塞原因。
